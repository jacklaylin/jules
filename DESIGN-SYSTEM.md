# Jules web design system

The current visual system adapts the founder-supplied [brief](docs/design-system/BRIEF.md) and [original tokens](docs/design-system/tokens.css) to the existing plain HTML/JavaScript app. The attached brief supplies visual guidance, not permission to build future screens or change supported shopping behavior.

## Scope and ownership

- `public/design-system.css` owns shared tokens, local fonts, typography, full-width gutters, header, controls, selection chips, focus states, dialog defaults and reduced-motion/forced-color behavior.
- `public/design-system.js` mounts the companion-page header once and preserves sign-out and the permission-controlled Admin link. Pages attach their own actions.
- `public/brand-ui.js` supplies the shared outlined wordmark, orb dot, request-driven thinking/completion states and favicon controller. SVG outlines come from the locally licensed Instrument Serif; the logo never depends on a fallback dotless-j glyph.
- `public/brand-mark.js` paints the same outlines and a frozen orb into PNG exports. `public/brand/` contains the wordmark and font-independent favicon frames.
- Page CSS owns composition only. Repeated controls belong in the shared layer; base control selectors have low specificity so explicit page compositions such as image overlays retain their positioning.
- `public/admin-console.js` mounts the owner console on every admin page: the standard companion header (via `mountHeader('admin')`, so Admin is the current page and Log out signs out of admin), a slim 40px strip of tool links under the header (current one underlined; it stays under the compact header, scrolls sideways on phones at 44px and leaves tables the full width), and the single owner sign-in. Its styles are the admin-console section of `design-system.css`, followed by the shared admin data components from the October 14 design handoff (status badges in tinted green/amber/red, each with a glyph and a word; tabs; filter chips with counts; data tables; stats; folds; `.confirm-dialog`, the owner confirmation that lists exactly what an action removes and keeps); admin page CSS owns composition only.
- **Data view** (admin table pattern, design in `design/admin-table-pattern-handoff.md`): every admin table page uses, top to bottom, optional views (`.dv-views`, quiet pills for a tab's sub-pages, linkable with `?view=`), one toolbar row (`.dv-toolbar`: status filter as a segmented `.seg` with counts, `.dv-search` with a `/` hint, a Filters menu and at most one butter primary action), one status line (`.dv-status`, with removable `.dv-token` filters, and "Refreshing…" in words while a refresh runs), dense 40px rows (`.dv-list`, `.dv-head`, `.dv-row`; the page sets `--dv-cols`) and a detail panel beside the list (`.dv-split.open` + `.dv-detail`; on phones the detail takes the screen). A page has one More menu (`.dv-menu`, at the right of the page header): the same actions on every tab, grouped by area, and an action that belongs to a tab opens that tab first; never a second ⋯ menu. Menus are `.dv-pop` popovers (`.dv-menu`, `.dv-filters`) positioned under their button by `anchorMenus()` from `admin-console.js`. Keys: `/` search, J/K move rows, Enter opens, Esc closes. Editable tables (inputs and actions in cells) use a real `.dv-table` with the same dense look, and `button.quiet` for low-weight row actions. **Long text in a dense row stays on one line:** wrap it in `.dv-clip` (ellipsis, the cell's `title` holds the full text) so rows keep 40px, and put a row's link on the cell's main word as `.dv-cell-link` ("Chat" opens the message), never a trailing "Open ↗" button that wraps onto its own line; on phones, where rows stack, a clipped line may run to two. **Calm admin:** one navigation layer per level, serif titles and sans everything else (no mono caps in admin), one coloured button per screen (`button.quiet` for every other control), views as plain text links, the status filter as the only pill group, and a Note column that shows exceptions instead of repeating defaults (no source when there is one, no "For them"). Keyboard hints appear once, beside the action they speed up. A page title above a data view is `.dv-title` (34px serif); a row of headline figures is a MetricStrip (see Admin components). A figure beside the title (a day's total) uses `.dv-heading` with a `.dv-heading-note`; a labelled toolbar input (a day picker) is `.dv-field`; quiet footnotes under a table are `.dv-note`. Purchase history, Knowledge, People and Costs use it. **Where knowledge came from** (Admin › person): `.kind` markers, always with the word: `.kind-said` a filled ink dot (they told Jules, stated or confirmed), `.kind-seen` a ring (counted from what they did: purchases, wardrobe, saves, likes, outfit photos), `.kind-inferred` a dashed ring (Jules's own reading). The person page's Summary tab is an AdminCard (`.dv-card`) profile table (one row per coverage dimension, coverage as a status badge) beside a quiet AdminCard (`.dv-card--quiet`) with what Jules would text now; rows stack as blocks on phones. Above them a `.dv-metrics` strip (taste coverage, weeks with a win, last positive request); beside the profile, an Adoption card (four week blocks: ok-green a win, `line-strong` asked but nothing liked, a dashed outline quiet) and a Chat quality card (one bar of how requests ended: ink positive, `line-strong` refined or moved on, `danger` turned down or missed, `line` no reply, each with its count in words). Bar widths are set through the style object, never a style attribute (the CSP blocks inline styles). The Knowledge tab is one `.knowledge-table`: their own facts (editable in place) and derived rows (read-only) together, filtered by kind chips, topic, source and search, sorted by any column header (`aria-sort`, an arrow on the header), with a brand's weight as a small ring. Header sort buttons drop the gel gloss.

## Admin components

The owner console has its own section in the Jules design system (Claude Design › Jules › Admin), founder decision October 22, 2026. Every admin page is built only from these; a page that needs something new adds it here first. The prod review and order of work are on the "Style report adoption in admin" canvas (board "Admin in prod").

- **Skeletons are admin's only loading state.** A section keeps its heading and draws Skeleton shapes at the content's size (`skeletonRows()` for tables and lists) until its data lands. No Aqua loader, no activity toast for reading a page (`adminFetch` reads with a plain `fetch`; only actions the owner takes go through `trackedFetch`), no "Loading…" text in titles or lists. A cached page refreshing behind its content says "Refreshing…" in the status line.
- **AdminPage:** `.dv-title` (34px serif) on every admin page, with an optional `.dv-heading-note`; one `btn--butter` at most, every other control `button.quiet`. Never `.app-heading` or a 64px title in admin.
- **MetricStrip:** `.dv-metrics` of cells built with `metricCell({label, value, detail, change, tone, was})` from `admin-console.js`: label, value, an optional detail line, then the change badge and the earlier value on one line (`shortVerdict` keeps the badge word short). No label cell; tone `ok` better, `fail` worse, plain for no change, New or too few. Cells share the width (140px min); two per row on phones.
- **MetricsHelp:** one `details.fold.metrics-help` under a strip: what each figure counts and which way is better.
- **AdminCard:** every titled block is a `.dv-card` with the title inside the box: `.dv-card-head` (h2 30px, `.dv-card-note`, `.spacer`, an optional link), the body, an optional `.dv-card-foot`. Tables inside have no box of their own. `.dv-card--quiet` is the fog variant for a read-only aside.
- **SplitBar:** how a total splits into parts (`.split-bar`, parts as spans with `flex-grow` set through the style object and a colour class: `is-ink`, `is-grape`, `is-strong`, `is-line`, `is-up`, `is-down`), with a legend of counts and percentages; `split-bar--compact` (8px) inside a table cell. Under 5 votes a card says "Too few votes" instead of a bar.
- **Admin › Style report** (`/admin/style-report`, was Report jokes; `/admin/jokes` redirects to its Jokes view): Engagement (MetricStrip with a Compare picker, How they shared, By card, By week; `lib/report-adoption.js`) and Jokes. Adoption shows the share loop as one AdminCard linking there.
- **Compare:** a `.dv-field` select in the toolbar, "This week vs last week" or "Last 4 weeks vs the 4 before". The windows and the change badge come from `lib/compare.js` (`windows`, `change`), so every strip reads the same way; Scorecard's verdicts use the same windows (`periodRanges` in `scorecard-view.js`). A figure with no earlier value to compare says so ("now only", or New before it was tracked), never 0.
- **AdminPage stack:** a page's AdminCards sit in `.dv-cards` (24px apart); a section that can be hidden as a whole is a nested `.dv-cards` holding its cards. MetricsHelp sits right under the strip. Secondary filters (Scorecard's "Whose searches") live in the Filters popover, so the toolbar keeps one filter group.
- **Admin › Costs:** a MetricStrip for the picked month (to date, projected month end against last month's whole total, today against the daily warning budget, lifetime) or day, with What these numbers mean holding the Billed/Estimate/Manual legend and each view's explanation; each view (By service, By feature, By person, Recurring jobs, Evals) is one AdminCard. Coverage, billed vs recorded, caps and job alerts stay in the status line on every view. Less spend is better, so a higher projection is red.
- **Person › Conversation and Wishlist:** Conversation's toolbar has one segmented filter (All · Problems, each with its count) and Load earlier as a quiet button; the iMessage bubbles keep Aqua (the one admin exception, because it shows what they saw). Wishlist is one AdminCard holding an AdminTable (Item, Stores, Price alert, Test alert); Test alert opens the rehearsal form in a full-width row under the item.
- **Retired** (October 22, 2026): `.data-table`/`.table-scroll` (use `.dv-table` in `.dv-table-wrap`), `.notice-bar` (a warning is a `badge warn` with words in the `.dv-status` line; an error is `.notice--error`), `.empty-state` (`.dv-empty`), `.dv-subhead` and `.dv-note` (an AdminCard head, note or foot, or MetricsHelp), and `.app-heading` in admin (`.dv-title`). `.mono-label` stays only as a group label inside `.dv-menu`.

## Visual rules

White page ground (signup is the one exception: see "Signup chat" below); neutral product-image surfaces. Ink `#17120F`, fog `#F3F1EE`, line `#E8E4E0`, secondary text `#6B625B`. Butter is the primary-action color; grape is for sharing and focus. Tangerine, bubblegum and grape form the orb. Aqua is reserved for iMessage bubbles and the indeterminate loader (never in admin).

Hairlines and card borders use `line`; text inputs, selects, textareas and `.field` use `line-strong` `#8A817A` (3.8:1, meets the 3:1 control-boundary rule). Selects share the text-field shell but drop the browser arrow for the Jules line chevron (`/brand/chevron-down.svg`, 22px, 16px in from the right, text stopping 52px short); a required select still on its empty prompt shows it in `text-2`, the border turns `ink` on fine-pointer hover, disabled is 45% opacity with the reason in words beside it, and the open option list stays native. Forced-colors mode restores the native arrow. Every colour shared CSS paints is a `:root` token, including the orb glow, gel gloss, `shadow-photo-control`, Aqua loader parts (`aqua-*`), iMessage details (`imsg-*`), `photo-overlay`, `backdrop` and the `shadow-dialog`/`shadow-panel` shadows. Page CSS reuses tokens rather than writing hex values.

Errors use `danger` `#B42318` (6.6:1) and always say in words what failed and the next step. An invalid field gets `aria-invalid="true"` (2px danger border) with a `p.error` message beneath it; a failed page or section uses a `.notice--error` box. Partial results stay visible.

Buttons are coloured by class only: `btn--butter` for the primary action, `btn--grape` for sharing, `btn--ink` for dark actions. Bare `<button>` elements get the white gel pill through a zero-specificity `:where()` rule. Shared CSS never targets page IDs or a page-level `.primary` class for button colour.

Wishlist photos use contain sizing to keep the full saved image visible in cards, retailer previews and the detail carousel. Loaded frames match a consistent image-edge background color; varied or unreadable edges fall back to white. Loading and unavailable-photo surfaces retain fog. Photos are never tinted, stretched or generated to fill the frame.

Instrument Serif roman supplies headlines; Bricolage Grotesque supplies body text and bold starter-pack titles; JetBrains Mono supplies small labels/data. All fonts and redistribution licenses are bundled in `public/fonts/`; no external font request or CSP expansion is required. The old Mongule/neon wordmark, random hover gradients and rotating display-font pool are no longer used by these pages.

Collection pages share their pieces through `design-system.css`, not page stylesheets: the `.collection-heading` title (large serif title), the `.filter-bar` row under it (`.filter-chips`, one pick per group, with `.chip-count` numbers, then the `.filter-count` item count, then an optional page action such as Add item; the row never wraps, see Filter row rules), the `.product-grid` of `.product-card` tiles (`.tile`, `.photo`, `.card-price`, `.card-state`, `.photo-pending`, skeletons), the round `.icon-button` photo controls (`.alert-toggle` upper-left, `.remove-item` upper-right) and the `.toast`. A new collection page, such as the wardrobe, reuses these classes rather than restyling cards. Photo frames cast no shadow.

**Filter row rules.** One pick per group; the selected chip is `.chip--on` with `aria-pressed="true"`, and tapping it again turns off only its own group. The wardrobe has one group (its categories). The wishlist has two, in one row: **Category** (All, then the wardrobe's categories in the same order and names, shared from `public/categories.js`; an item's category comes from its tag, and an untagged save is only in All) and, after a 1px `line` hairline (`.filter-divider`), **Show** (`.chip--state`: Alerts on, Sold out and Bought, each led by the line icon its card shows, so they never read as categories). Each group is a `.filter-group` with `data-group` and an `aria-label`. One category and one state combine (Shoes + Alerts on shows shoes with alerts on), and All clears both. Each chip keeps its own count whatever else is on, so the row doesn't shift while you tap; the row's count says what the combination shows. Categories show only when one would narrow the list. A chip shows only when it has items, except the selected chip after its last item is removed: it stays at 0 beside an empty state with Show all until the person leaves it. With nothing to filter, `.filter-chips` is empty and hidden and the row shows just the count, which reads "6 items" or "3 of 6 items" while filtered. The wishlist keeps its filters in the URL (`?category=shoes&filter=alerts`; `filter` is `alerts`, `sold-out` or `bought`); a link to an empty filter opens All. **Hidden chip:** the wishlist's Bought chip is the one exception to "every chip is a subset of All": items the person marked "I bought this" leave All (and every other chip's count) and appear only under Bought, whose count reads "3 bought". **Never wraps:** the row shows the chips only while every chip, the count and the action fit on one line, at any width (so the wishlist keeps its pills on a phone). Otherwise `fitFilterBar(bar)` from `public/filter-bar.js` swaps the chips for one Filter button (`.filter-menu__trigger`, the selected choice and its count, `ink` when a filter is on, with a round × to clear it on desktop) that opens the same choices as rows with counts and a check: a popover under the button on desktop, a sheet with a "Filter" title on phones. A row clicks the matching chip, so the page's own filter logic runs; with one group a row choice closes the menu. With groups, the button joins both picks ("Shoes · Alerts on") with the count they show (the page's `data-shown` on `.filter-chips`), the menu has a section per group (mono `.filter-menu__section-title`, rows with the chip's icon), and it stays open while you pick, with Clear and a butter "Show N items" in its `.sheet-foot`; switching back to chips needs a little spare room so a window on the limit doesn't flicker. Pages call `fitFilterBar` once and keep rendering chips as before. On phones in menu mode the button drops its count (the row's count says it) and the count may take two short lines. Never offer a filter for a state the page can't verify (no "In stock" for a store that hasn't been checked).

**Stock states.** "Sold out" is an ink `.stock-tag` (white mono caps), shown on a wishlist card, a product-page store row or the product summary only when every store link was checked and reported sold out, and the check is under 3 days old. An older reading drops to a dated `text-2` `.card-note` ("Sold out when checked Oct 4"); an unchecked or unverified store is unknown and gets no tag. Ink means you can't buy it now; butter stays for good news (a price drop, or "Best price": a butter `.stock-tag.best-price` before the price on the one store row whose page-read price is strictly the lowest among at least two in-stock stores in one currency; ties, a lone store, an unreviewed store and indexed or unverified prices get none). A store the better-price scan found outside the trusted list says "· unreviewed store" after its price. One stock badge per card, and photos are never dimmed or covered. On the product page the state sits in a bordered `.stock-summary` box under the price with one butter "Text me when it's back" button (it opens the size picker and saves a restock alert), or a `text-2` line once an alert is on; sold-out store rows sort last. These classes live in `wishlist.css` until a second page needs them.

**Sheets.** Every bottom sheet (the phone Filter sheet, the style report's What's off, Edit your receipt and Share sheets), and any dialog that can grow taller than the screen, is a `dialog.sheet` in three parts: `.sheet-head` (title and round ×), `.sheet-body` and an optional `.sheet-foot` (Cancel, Done). The head and foot stay put; only the body scrolls between them, so the title and × are always reachable. Cap the sheet's height (`max-height` in `dvh`) and let the body take the rest. Opening a sheet focuses the sheet itself, never a row inside it: a focus ring on something that was just tapped open reads as a stray highlight on touch screens. Keyboard users Tab to the rows and get the grape ring there.

Actions use one gel-pill vocabulary with 44px minimum targets. Selected radio chips retain native inputs. Wishlist chooses its desktop column count from the available width, using a 280px minimum card width and a maximum of four columns, and uses two on phones, with equal-height rounded cards, portrait image slots, bold product titles and mono price labels. Photo-pending slots use the orb and an honest status label. The alert bell sits at the upper-left, with ink on butter and an ON badge when active. Removal is the × at the upper-right, matching the round close × on dialogs, so a top-right × always gets rid of something; it has an accessible label and undo. Both photo controls are the same flat circle as `.close-button` (1px `line` border, no gloss or lift) on `photo-overlay`, plus `shadow-photo-control` so they hold on a white photo. Product details use the same saved product title and have no refresh or removal controls. Saved metadata renders before background photo recovery; opening a product shows its known summary immediately. Desktop heading is Wishlist; mobile heading is Your wishlist with the count beneath. Shared dialogs use rounded borders, visible focus and keyboard support. Every dialog, sheet, admin tool panel and the phone menu closes with the shared `.close-button`: a 44px round × (inline 2px-stroke SVG, 16px) with a 1px `line` border, an `aria-label` naming what it closes, top-right in a `.dialog-heading` row beside the title. No "Close ×" or "Close" text buttons. Main/header align to `--page-gutter` (5vw), without a centered outer max-width wrapper.

The header retains a compact scroll state without shifting body spacing. Desktop shows serif Wishlist, Wardrobe, Your style, permission-controlled Admin, and Log out links, each section colour-coded with one Jules colour (Wishlist butter, Wardrobe tangerine, Your style bubblegum, Admin grape): a 4px bar grows from the centre under the label on hover/focus and stays under the current page. Labels stay ink/`text-2`, the bar is drawn under the text so nothing shifts, and the orb is not used as a nav marker. At 800px and below, a gel Menu button opens a full-screen white modal with the same navigation nodes in a vertical list; the current page keeps its 6px colour bar. Escape/Close restores focus and page scrolling; resizing to desktop closes the menu. Admin-link permissions and logout handlers remain attached to the same elements. The last header item is the **Account** avatar (`.nav-account`): a 38px fog circle with a person outline in the desktop bar, grape-bordered on hover and on `/account`. In the phone menu it drops the avatar and becomes a quieter text row: "Account" in 32px serif, `text-2` (ink on `/account`), under a 1px `line` hairline, so it reads as a setting rather than a fourth section. The close × SVG carries its own `width`/`height` so it keeps its shape even if a stale stylesheet is cached. The menu footer reports the actual wishlist count when available and is cleared on sign-out.

### One pill, then quiet rows (secondary actions)

A screen that ends with several next steps uses one coloured gel pill for the single most useful action, then lists the rest as quiet rows (founder, October 16, 2026; first used on the style report end screen). Don't stack several equal-weight pills or split secondary actions into half-width pills.

- **Primary:** one full-width gel pill, 56px tall. Grape when the action is sharing, butter otherwise. If a prerequisite is missing (for example an unlinked order source), that prerequisite takes the pill and the usual primary drops into the rows.
- **Rows:** full width, at least 56px tall (48px on screens under 640px tall, still above the 44px touch minimum), separated by 1px `line` hairlines with one above the first row. Each row is a 22px icon, a 12px (`space-3`) gap, the label in Bricolage 600 16px `ink`, and an optional `text-2` "↗" at the far end when the row leaves the page (Messages, another site). No pill, fill, gloss or shadow; hover turns the label grape on fine pointers; focus is the grape ring drawn inside the row.
- **Shared classes:** `.action-rows` (the container, with the hairline above the first row) holding `.action-row` buttons or links; a `.action-row__go` span carries the end mark ("↗" or "→"). Onboarding's connect screen and the wardrobe item detail (Fix details, Remove under "What goes with this?") use them; the style report end screen still has its own copy. A leading icon is an `svg` before the label `span`; the label takes the free width.
- **Choices on a row open in place, not in a second dialog.** When a row inside a dialog needs one more answer (the wardrobe's Remove asks why), the row turns into its question with a 44px round × to cancel, and the answers follow as one wrapped line of compact chips aligned under the label. One tap answers and acts; Undo comes from the toast. Never stack a dialog on a dialog. Shared classes in `design-system.css`: `.row-ask` (holding `.row-ask__head` with the icon, question and `.row-ask__cancel` ×, then `.row-ask__chips`); the wishlist's "I bought this" (which store?) uses it too.
- **Rows under a list.** When the rows follow a list whose items already end in a 1px `line` hairline (the wishlist's store rows, `.links`), that last hairline is the rows' top line: no second rule and no empty band between two (`.info .links+.action-rows` in `wishlist.css`). The wishlist item detail runs photos, name, price, stock or alert status, store rows, action rows ("I bought this", "Remove from wishlist"), then the activity line ("Sent · Price checked", 12px `text-2`) 24px below the last row. Actions never sit under the activity line. The app has no `--space-*` custom properties (the scale lives in the design system's tokens), so page CSS writes the px value.
- **Leaving:** Exit or Close is a 44px round × button in the top-right corner (1px `line` border on white), not a row or a text link. On the desktop stage the window's own close button replaces it.
- **Icons:** line icons on a 24px grid, 1.8px stroke in `currentColor`, round caps and joins, no fill, `aria-hidden` beside a visible label. Current set: share (arrow out of a tray), link (two chain links), chat (speech bubble), replay (circular arrow), edit (pencil), remove (bin) and close (×, 2px stroke). Draw a new icon in the same style rather than adding an icon set or emoji.

On dark grounds (the desktop story stage) the same hierarchy holds: Share is the one filled grape gel pill, and the other controls (thumbs, Edit lines, Shuffle, close, arrows) are quiet outlines, a 1.5px white border at 35% opacity over a 5% white fill. A pressed thumb fills with butter.

## Activity and motion

`public/activity.js` tracks concurrent requests and local workflows. It shows the actual current action and that action's elapsed time. Quick actions (a thumb, a remove, a save) answer with their own motion and toast, so the panel appears only for a request still running after one second; Jules' own work (style analysis, shopping chat) shows it at once. The orb and Aqua loader replace the old spinner. Private image fetches retain neutral per-image placeholders without flashing the page activity panel.

Only explicit style analysis and shopping-chat POST operations trigger the header dot hop and favicon frames. Loading pages or saving notes does not imply a store search. Other agent workflows can explicitly pass `{agent:true}` to `withActivity`. HTTP errors and thrown failures suppress successful completion for that activity batch. The next batch can recover normally.

The orb spins in 7s and wobbles in 4s. Thinking hops in an 8s loop, with horizontal distances calibrated to the outlined letters and a smaller return arc inside compact headers; successful completion has a short landing pop. Favicon frames swap every 350ms and settle to the static icon. Hidden tabs stop favicon intervals. Reduced motion disables all decorative animation, including typing, entrances, hover transitions and favicon swaps, while retaining readable status text. The Aqua capsule is indeterminate and never represents measured progress.

Micro-motion uses Motion's free `animate()` (mini) and `spring`, vendored at `public/vendor/motion-mini.js` (about 5 KB gzipped; the CSP allows only same-origin scripts, so no CDN). Pages never import it directly: `design-system.js` exports `closeDialog` (a 160ms exit for the panel and backdrop before `close()`, so `close` listeners still run once the dialog has gone; Escape on any modal uses it), `removeWithMotion` (fade a card out, then spring its siblings into their new places), `popIn` (springy confirmation when a control turns on, such as the price-alert bell), `answerWithMotion` (a thumbs answer: the chosen thumb fills butter and springs with a nod toward its meaning, the other fades back, then the question drops away before the answered state replaces it; used by wardrobe photo suggestions) and `riseIn` (toasts rise into place). Every helper is instant under reduced motion, and exits also settle on a timer when the browser pauses animations. Entrances stay in CSS. Close a dialog with `closeDialog` rather than `dialog.close()`, except for instant resets such as sign-out.

## Public landing page

The public `/` page is a single-screen layout with an autoplaying iMessage demonstration. Each page load plays one conversation chosen at random (Satisfy x HOKA sneakers, or a Balenciaga Rodeo resale-vs-dupe search); the end shows Replay and Shuffle topic, which always switches to a different conversation, with responsive composition in `public/landing.css`. `public/landing-timeline.js` holds each conversation’s duration and typing windows and supplies deterministic progress and typing states; typing windows must end exactly when the matching Jules message appears in `index.html` (tested). Bubbles retain their full 450ms sender-corner entrance; typing indicators precede Jules replies, and the chat scrolls to new messages over 700ms. Autoplay starts on load; page scrolling does not drive the demo. Reduced motion displays the complete chosen conversation, with Shuffle topic but no Replay; an inline screen-reader transcript is also available without JavaScript. The example conversations are labeled illustrative; their listing prices were captured from real listings and will drift. FAQ, Privacy and Terms sit as a quiet `text-2` line (`.landing-legal`) in the stage's bottom-left corner on desktop and centred under the actions on tablets and phones, so the page still never scrolls. The example prices are dated ("Prices as of October 2026") only in the screen-reader transcript, not on screen (founder, October 20, 2026). `/faq`, `/privacy` and `/terms` share `legal.css` (designed on the "Legal links and pages" Claude Design canvas): the public header with a FAQ/Privacy/Terms nav (ink bar under the current page), a sticky "On this page" list beside one 720px column on desktop, and the same FAQ/Privacy/Terms line in the footer. Privacy and Terms open with a bordered "The short version" card; the FAQ is one `.faq-item` section per question, and its FAQPage JSON-LD must repeat the visible questions and answers word for word (tested in `tests/seo.test.js`).

`mountPublicHeader` in the shared JavaScript hydrates public-page logos, while the shared gel links and header navigation primitives serve `/`, `/signup` and `/login`. ## Verification before shared changes ship

**Load speed** (every page and tab, October 22, 2026). Before a page ships, check and report in the PR:
1. A return visit draws the last content at once from `public/list-cache.js` (`saveList`/`readList` for one list, `readPage`/`savePage` for an admin report, `readView`/`saveView` for a person's tabs), then refreshes behind it. ## Signup chat and the Jules avatar — October 19, 2026

`/signup` is a short chat with Jules instead of a form, designed on the "Signup redesign" Claude Design canvas. "Text jules." is the only logo on the page (no shared header); on phones it shrinks to a compact heading after the first answer. Composition lives in `public/signup.css`; the flow lives in `public/signup.js`, with pure helpers in `public/signup-chat.js` (name split, birthday mask and validation, star sign, outcome lines) and the phone-format check shared with the server in `public/signup-phone.js`.

- **The one exception to the white ground.** Signup sits on an animated haze of the brand colours (`haze-*` tokens: two blurred gradient layers drifting on 22s and 17s loops). Reduced motion stops it. No other page uses the haze.
- **Jules-native chat, not iMessage.** The real iMessage look belongs to Messages only, so the hand-off feels real. Jules's lines are outlined frosted bubbles (1.5px ink, `frost` fill, Bricolage 17px) with the still-orb avatar; your answers are ink gel pills you can tap to change until the signup is sent. Quick replies are the shared radio chips. The compose box is an ink-outlined pill with a butter send button. No SF font, grey/blue bubbles, tails or aqua.
- **Questions, in order:** name (one answer, split at the last space; a single word gets "and your last name?"), birthday (one numeric box auto-formatted as MM / DD / YYYY; Jules reacts with the star-sign symbol worked out from the date), gender chips, mobile number, then the unchanged consent disclosure as an unticked checkbox card and one butter **Have Jules text me** button. Every answer is a real labelled input. Format errors (date, number, under 18) come back as a Jules line in `danger` and the same question stays open.
- **Ending:** Jules's closing lines come from what the server reports (`outcomeLines`): sent, delivery unconfirmed, already onboarding, waitlisted or saved. It never claims a text that wasn't confirmed. With a `text_url`, **Open Messages ↗** follows; "Wrong number? Start over" keeps the other answers and re-asks the number.

**Avatar.** Jules's avatar is the orb, frozen and filling a circle: `public/brand/avatar-orb.svg` (web chat, 26px), `avatar-orb-1024.png` (round, transparent corners) and `contact-photo-1024.png` (full-bleed square for the contact card and the Photon line's iMessage Name and Photo; iOS crops it round). Avatars never animate, so a thread of Jules lines doesn't fill with spinning dots; only the logo's dot moves. The app-icon j is not cropped into a circle for an avatar (its hook gets cut off and it doesn't read at 26px). The design system's Orb component and Avatar asset group carry the same rules.

## Rich link previews (LinkPreview) — October 22, 2026

Every rich iMessage preview image is one component, LinkPreview, designed on the "iMessage link previews" Claude Design canvas. The template lives in `scripts/link-preview-template.js`; `node scripts/build-link-previews.js` renders the static images into `public/brand/previews/` (see [RICH-PREVIEWS.md](RICH-PREVIEWS.md)). New previews use it; don't draw one by hand.

- **Frame:** 1200×630. Headline top-left (Instrument Serif 112px, line-height 0.9, `-0.04em`, balanced line breaks) in a 590px column that starts 72px from the left and 64px from the top. The logo (outlined wordmark, 150px wide, still orb dot) sits bottom-left, 60px from the bottom. **No eyebrow.** iMessage prints the page title and domain under the image, so the headline should not repeat the title.
- **Right side:** what the link opens, drawn as tilted cards (rotated −11° to +9°, 24px radius, soft ink shadow), allowed to run off the right and bottom edges, kept at least about 80px clear of the headline. Use real card titles from the product ("How niche is your taste?", "What's in, what's out?", "Where do you sit on the spectrum?") with blank bars, unlabelled gauges and empty photo slots. Never invent prices, stock, scores, names or counts. The homepage chat is labelled marketing art.
- **Haze background:** one haze per surface, so a preview is recognisable before anyone reads it. Each is a base colour plus nine blurred, irregular blobs of brand colours placed by a fixed seed. They stay mostly on the right two-thirds; two faint ones on the left keep the headline readable. Previews are images, not pages, so the haze is allowed here alongside signup.
